Feather API 缺口报告 — 建筑合成交互设计阶段的交叉核验发现

本文档是 DockovDrinks 模组在开发"饮品制作台建筑合成交互"功能过程中，对 Feather 框架交互系统进行交叉核验后整理的 API 缺口汇总，面向 Feather 框架维护者。

背景简述如下：DockovDrinks 需要为饮品制作台建筑添加合成交互入口（Crafting）以及技能树交互入口（PerkTree）。初步设计是使用 InteractionUtils.AttachViewInteract 给建筑的 functionContainer 挂载两个 ViewInteractHandler 组件，一个指定 GameViews.Crafting 配合 viewParam 作为配方标签过滤，另一个指定 GameViews.PerkTree 配合 viewParam 作为技能树 ID。在对 Feather 框架源码（FastModdingLib/）、Duckov 原版反编译代码（assembly_0625/）以及 DockovDrinks 现有实现（Building/BuildingConfig.cs、Npc/NpcConfig.cs）进行交叉核验后，发现该方案在多个层面存在问题，以下逐一列出。

第一个缺口是 InteractTemplates 缺少 Crafting 交互模板。Feather 框架在 UI/InteractTemplates.cs 中提供了三个开箱即用的交互模板类：BuildingInteractTemplate 用于打开建造界面，PerkTreeInteractTemplate 用于打开技能树，EndowmentInteractTemplate 用于打开天赋面板。这三个模板均继承自 InteractableBase，在 OnInteractFinished 中通过 ViewDispatcher.Open 打开对应的 View。然而模板列表中缺少一个 CraftingInteractTemplate。对于"给建筑挂载合成交互"这一常见场景，Mod 开发者没有任何声明式的模板可用，只能退而使用底层的 InteractionUtils.AttachViewInteract 手动指定 GameViews.Crafting 和 viewParam，或者绕过 Feather 框架直接使用 Duckov 原版的 InteractCrafter 组件——后者在 Feather 体系下缺乏生命周期管理和 Mod 卸载自动清理保障。建议新增 CraftingInteractTemplate 对标 PerkTreeInteractTemplate 的设计：公开一个 CraftingTag 字符串属性（对应配方的 Tags 过滤），在 OnInteractFinished 中调用 ViewDispatcher.Open(GameViews.Crafting, CraftingTag)。同时该模板需要设置 overrideInteractName 和 _overrideInteractNameKey 以支持交互提示文本的本地化，该问题的详细讨论见后续的交互名缺口。

第二个缺口是缺少公开的通用多交互组装 API。NPC 的多交互机制——即一个 NPC 同时提供商店、任务、技能树等多个交互入口——是通过 FriendlyNpcUtils 内部的 SetupInteractionGroup 私有方法实现的。该方法的逻辑包括以下步骤：按优先级（商店优先于任务优先于技能树）选定主交互体 primary，将其余交互体加入 primary.otherInterablesInGroup 列表，设置 primary.interactableGroup = true，然后遍历成员禁用其独立碰撞体（interactCollider.enabled = false）、隐藏独立交互标记（MarkerActive = false）、并将成员的位置和标记偏移同步到主交互体。这套逻辑完全写死在 FriendlyNpcUtils 的私有作用域内，没有任何公开的 API 可供 Mod 在建筑或其他非 NPC 场景中复用。如果 Mod 开发者需要给建筑挂载两个交互（如 Crafting 加 PerkTree），目前必须自己重新实现一整套交互组管理逻辑：手动创建独立子 GameObject、手动设置 interactableGroup 和 otherInterablesInGroup、手动管理碰撞体启用和禁用状态。这些步骤极易出错，且与 Feather 框架提供的 InteractionUtils 体系脱节——InteractionUtils.AttachViewInteract 完全不知道 interactableGroup 的存在，每次调用只是简单地向 target 添加一个新的 ViewInteractHandler 组件。如果两个 ViewInteractHandler 挂到同一个 GameObject 上，它们共用同一个 trigger Collider，游戏交互系统通过 OverlapSphere 找到两个 InteractableBase 时没有内置的选择机制，玩家按 E 键只会触发其中一个而无法选择。建议将 SetupInteractionGroup 的核心逻辑提取为 InteractionUtils 的公开方法，签名可设计为 SetupInteractionGroup(InteractableBase primary, params InteractableBase[] members)，或者封装一个 Builder 模式的 InteractionGroupBuilder，使任意场景下的多交互组装都能以声明式方式完成。

第三个缺口是 ViewInteractHandler 不设置交互名。Duckov 原版的 InteractableBase 通过 overrideInteractName（布尔值）和 _overrideInteractNameKey（本地化键字符串）两个字段控制交互提示文本。当 overrideInteractName 为 true 时，游戏交互 HUD 显示 _overrideInteractNameKey 经 ToPlainText() 翻译后的文本。在 NPC 模式中，NpcShopInteract 设置了 overrideInteractName = true 和 _overrideInteractNameKey = "UI_Trade"，QuestGiver 设置为 "UI_Interact_Quest"，PerkTreeUIInvoker 设置为技能树 ID。然而 Feather 框架的 ViewInteractHandler（Interaction/Components/ViewInteractHandler.cs）完全没有涉及这两个字段。ViewInteractHandler 的完整源码只有三个成员：ViewType、ViewParam 和一个仅调用 ViewDispatcher.Open 的 OnInteractFinished 重写。这意味着通过 InteractionUtils.AttachViewInteract 创建的任何交互点，其交互提示文本将保持 InteractableBase 的默认行为——要么显示空字符串，要么显示不可读的组件名称——玩家在游戏中对建筑按 E 键时看不到任何有意义的交互提示，严重损害用户体验。这个问题在单交互场景下只是体验降级，但在多交互场景下是功能故障——如果两个交互都没有显示名称，玩家根本无法区分应该选择哪一个。建议为 ViewInteractHandler 增加 InteractNameKey 字符串属性，并在 AttachViewInteract 的初始化流程中自动设置 overrideInteractName = true 和 _overrideInteractNameKey = InteractNameKey。或者，在 InteractionUtils.AttachViewInteract 的参数列表中增加可选的 interactNameKey 参数，使 Mod 开发者无需在 Attach 之后手动获取组件实例并设置私有字段。

第四个缺口是 Building.functionContainer 的访问路径不透明。Duckov 原版的 Building 类通过两个 SerializeField private 字段定义了建筑的两个子容器：graphicsContainer（美术层，包含非 trigger 的物理碰撞体，用于防止玩家穿过建筑）和 functionContainer（功能层，包含 trigger 交互碰撞体，用于交互检测）。Feather 的 BuildingUtils 内部使用 SetBuildingField 和 GetBuildingField 这两个 private 反射辅助方法来读写这些字段，因此 BuildingUtils 自身可以正常操作 functionContainer。但这些辅助方法并未公开给 Mod 开发者使用。当 Mod 需要在建筑建成回调（BuildingUtils.OnBuildingBuilt）中获取 functionContainer 以挂载交互组件时，唯一可行的方法是硬编码 building.transform.Find("Function")。这种硬编码方式存在两个隐患：如果未来游戏版本或 Feather 框架修改了子对象命名约定，代码将静默失效且不会在编译期报错；它绕过了 Feather 的类型安全体系，将字符串约定扩散到了 Mod 代码中。建议 BuildingUtils 增加两个公开方法：GetGraphicsContainer(Building building) 和 GetFunctionContainer(Building building)，利用已有的反射逻辑安全地返回子容器引用，从而消除硬编码字符串依赖，并使 Mod 的交互挂载代码与 Feather 建筑系统的内部实现解耦。

第五个缺口是最根本性的架构问题——Duckov 原版交互通道与 Feather View 调度通道之间存在分裂。Duckov 游戏原版提供了一套成熟的交互组件体系，包括 InteractCrafter（用于合成工作台交互）、PerkTreeUIInvoker（用于技能树交互）、NpcShopInteract（用于商店交互）、QuestGiver（用于任务交互）等，它们继承自 InteractableBase，各自在 OnInteractStart 或 OnInteractFinished 中直接调用游戏原生 UI 入口（CraftView.SetupAndOpenView、PerkTreeView.Show、StockShop.ShowUI）。Feather 框架在此基础上构建了另一套 View 调度通道：ViewDispatcher 维护 Identifier 到 Action 的映射表，InteractionUtils 通过 ViewInteractHandler 将交互事件转发到 ViewDispatcher.Open，再由 ViewDispatcher 中注册的 handler 间接调用游戏原生 UI。这两套通道的后端最终指向同一个 UI 入口——ViewDispatcher 中为 GameViews.Crafting 注册的 handler 确实调用了 GameUIUtils.OpenCraftingView，为 GameViews.PerkTree 注册的 handler 确实调用了 PerkTreeView.Show——因此从 UI 打开的角度看，两套通道是等效的。但前端交互层的管理能力存在显著差距。原版通道的组件自带完整的交互名本地化（overrideInteractName + _overrideInteractNameKey）、标记偏移设置（interactMarkerOffset）、碰撞体配置（独立的 SphereCollider 或 BoxCollider），并且天然支持通过 interactableGroup + otherInterablesInGroup 进行多交互组装。Feather 通道的 ViewInteractHandler 则是一个极简封装——它只负责在交互完成时将 ViewType 和 ViewParam 传递给 ViewDispatcher.Open，不处理交互名、不管理碰撞体、不支持多交互分组。这种分裂导致了一个尴尬的 trade-off：Mod 开发者如果选择 Feather 通道（通过 InteractionUtils.AttachViewInteract），会失去原版通道提供的交互名和多交互能力；如果选择原版通道（直接使用 InteractCrafter 等 Duckov 原生组件），则会失去 Feather 框架提供的生命周期管理、Mod 卸载自动清理、以及 Identifier 体系的类型安全保障。建议 Feather 框架在两个方向中至少选择一个进行补全：要么增强 ViewInteractHandler 使其具备原版组件的完整能力（交互名本地化、标记偏移、多交互分组），使 Feather 通道成为原版通道的完整上位替代，让 Mod 开发者无需在两个通道之间做能力与安全的取舍；要么提供原版组件的 Feather 封装（如 FeatherInteractCrafter 包装 InteractCrafter），在保留原版组件全部能力的同时加入 Feather 的生命周期管理和注册表清理机制。

以上五个缺口分别涉及模板完备性、多交互架构、交互体验、类型安全和架构一致性。其中第五个缺口是最根本的设计问题——它导致 Feather 交互系统在"简单场景"（创建独立的单一交互点）下表现良好，但在"复杂场景"（给建筑添加带交互名的多交互入口）下迫使开发者绕过框架直接操作原版类型。DockovDrinks 的当前短期方案是：建筑只挂载单一 Crafting 交互（通过 AttachViewInteract + GameViews.Crafting），PerkTree 交互维持通过 NPC 的 FriendlyNpcConfig.PerkTreeId 既有实现，从而避免了多交互组装的复杂性。但这只是规避而非解决。随着项目扩展——例如未来饮品制作台可能需要同时提供 Crafting 加 PerkTree 加 Storage 等多重交互——这些缺口将从"需要变通"升级为"阻塞开发"。
